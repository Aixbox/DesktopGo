# DesktopGo 柔雾材质后续实现方案

日期：2026-11-11。**执行状态：第4节 Launcher 基准已实施；后续按外观参考与透色反馈适配，两种主题均改为模糊壁纸与半透明中性色混合，第5节通知式配方仍未接入。**事实依据见 [分析总报告](analysis.md)、[桌面报告](launcher.md) 和 [系统卡片报告](systemui.md)，当前算法与验证见 [柔雾实现记录](../../coloros-folder-material.md)。以下保留最初方案的目标、选择条件与验收约束，不将后续适配参数改写成原生事实。

基准阶段已执行：删除附加雾色函数及调用、移除浅深色整面渐变、将 CSS 与同步器统一为单层纹理，并更新相关公式与渲染测试。后续保留 `applyLauncherFolderMaterialColors` 作为原生参照，产品入口共享混合逻辑：浅色为 60% 模糊壁纸与 40% 中性浅灰，深色为 50% 模糊壁纸与 50% 近黑。两种主题的回退同步为各自的半透明罩层；成功纹理已包含背景，不再降低纹理或容器 opacity。明确的浅色参考及后续深色透色反馈推翻了此前压缩背景差异的方向，当前目标是恢复背景的明暗和透色，参数仍属于适配。圆角、布局、筛选玻璃、焦点轮廓和设置兼容值保持现有行为。证据摘录是归档时快照，不随实现改动重写。

## 1. 先确定要还原的表面

当前用户原始目标是桌面文件夹材质，并要求文件夹、Dock、搜索框一致。因此推荐先以 **Launcher 文件夹的正常模糊分支**建立可解释的基准；不要因为通知卡片更黑，就暗中换成通知配方。

| 实现目标                     | 应用方法                                                                     | 必须明确的边界                                                |
| ---------------------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------- |
| 对齐 Launcher 文件夹正常模糊 | 保留已核实的日夜两步公式，去除无原生依据的附加雾色和整面渐变，复查取样与分支 | 不能承诺必然更黑；该深色公式会抬起极暗部                      |
| 采用通知式深色观感           | 将 SystemUI 四步配方作为独立的候选材质策略，浅深色均有明确规则               | 这是借鉴系统通知的 DesktopGo 设计，不是 Launcher 文件夹原配方 |
| 确认目标设备走普通背景分支   | 按证据实现半透明底色及无模糊状态                                             | 不能假装该分支仍有高斯模糊，也不能将回退黑色再叠到正常材质上  |

本方案建议先做第一项。若后续目标明确转为“深炭灰系统卡片”，再实现第二项；不需要为研究比较立即增加用户设置、持久化字段或新的材质名称。候选策略可以先由纯函数和测试固定输入比较，最终只接入选定的行为。

## 2. 保留的产品要求

- 文件夹圆角、连续曲率、尺寸、图标布局和点击区域沿用现有实现。
- 文件夹、Dock、顶部搜索框继续共享一个材质策略和同一套纹理生成流程；不同位置按各自下方壁纸取样。
- 搜索框外层负责画材质，输入框保持透明；保留筛选按钮自身的玻璃底色、边框和悬停样式。
- 焦点轮廓继续贴合表面，`outline-offset: 0`；不得引入焦点环与表面间的空隙。
- 用户可见名称保持“柔雾”。现有持久化值 `coloros` 只作为兼容标识保留，不因本次研究自动迁移。
- 打开后的文件夹面板、搜索结果面板、筛选菜单以及普通应用图标不纳入这次材质修改。
- 不将原生条件高光替换为所有状态常驻的明显白框；保留拖拽、键盘焦点等功能性提示。

## 4. Launcher 基准方案

### 4.1 配方与顺序

以下为 Android ARGB，先转换为归一化 RGB 和 alpha：

| 主题/壁纸      | 第一步          | 第二步                 |
| -------------- | --------------- | ---------------------- |
| 浅色普通壁纸   | MIX `#3D2E3033` | DODGE_BG `#FF37393E`   |
| 浅色亮壁纸     | MIX `#1A000000` | 透明第二步，无颜色作用 |
| 深色，两种壁纸 | MIX `#33999999` | OVERLAY `#A3737373`    |

维持 `applyFolderMaterialColors` 的原生公式职责。如果选择严格的 Launcher 基准，从正常纹理生成链移除 `applyFolderMaterialVeil` 的附加灰色作用，并将两个主题的整面纵向渐变关闭。只删除已经没有用途的函数/变量，不连带重构几何或同步逻辑。

灰色附加层移除后，要同步更新依赖它的浅色测试期望。例如无蒙版的均匀 `#096692`，原生普通浅色输出是 `#1773A3`，亮壁纸分支为 `#085C83`；不能继续拿当前附加雾色后的 `#3B87AE` 作为严格原生基准。

深色基准数值仍为 `#096692 → #23698D`。实现验收不能一方面要求此原生数值，另一方面又要求所有背景都比原图明显更黑。

### 4.2 底图与回退不重复叠色

沿用桌面 cover 取景、现有用户背景蒙版、边缘扩展和高斯模糊，再执行一次颜色变换。用户蒙版是否参与是 DesktopGo 的取样契约，应与实际显示背景一致并在文档中说明；不要为了追求更黑悄悄额外增加材质专用蒙版。

正常结果为已完成混色的不透明纹理，普通背景只提供尚未解码、渲染失败或无壁纸时的替代显示。回退夜间 `#4C000000` 不得在成功纹理上方再次绘制。错误恢复成功后必须替换旧回退，避免同一表面同时保留两套颜色处理。

保留当前 WebView2 不依赖 `backdrop-filter` 的共享 Canvas 方案。原生参数800、450的单位未知，不将它们直接作为 CSS blur 值；调整32 CSS px需要独立说明适配理由。

### 4.3 壁纸分类的已知边界

原生 Java 分支亮度阈值为196；目前项目使用32×32采样和 alpha 加权亮度。保留195/196边界测试，但说明 JNI 的实际亮度度量未解析，不把这个近似宣称为所有壁纸分类完全一致。

均匀纯色经过高斯模糊不会凭空出现纹理。不要以“看不见模糊”为由无限增加半径或再加灰色。对纯色背景的表面分离度是配方目标，需要与原生基准明确区分。

## 5. 若选择通知式材质，如何实现

### 5.1 使用完整配方，不拼接两个表面的部分规则

普通通知在 `blurAmount=1` 时所选参数按以下顺序运行；top/bottom 只表示混色层：

| 顺序       | 浅色                   | 深色                   |
| ---------- | ---------------------- | ---------------------- |
| 面板第一步 | LUMINOSITY `#99333333` | LUMINOSITY `#A6404040` |
| 面板第二步 | OVERLAY `#80999999`    | OVERLAY `#80999999`    |
| 卡片第一步 | LUMINOSITY `#B3CCCCCC` | LUMINOSITY `#CC262626` |
| 卡片第二步 | DODGE `#73BFBFBF`      | OVERLAY `#66383838`    |

这是替代颜色策略，不能接在 Launcher 两步之后形成六步，也不再附加 `#CC333333` mask。普通通知、悬浮通知、低高斯和堆叠层的配方不同；本项目没有这些状态时，不必实现整个 Android 状态系统。

如果最终仅将深色替换为通知式、浅色继续使用 Launcher，必须明确记录为 DesktopGo 混合设计，并测试主题切换；不能把这种组合描述为某个原生控件的完整日夜配方。

### 5.2 混色算法契约

输入为已经模糊的不透明 RGB，计算时使用浮点数，完成所选步骤后再统一量化到8位。色值解析集中处理 Android ARGB，避免把 alpha 读成红通道。

对原色 `d`、参数色 `s`、参数 alpha `a`：

```text
MIX(d, s, a) = d × (1-a) + s × a

OVERLAY(s, d) = d < 0.5
  ? 2 × s × d
  : 1 - 2 × (1-s) × (1-d)
结果 = MIX(d, OVERLAY(s,d), a)

DODGE_BG(s, d) = d / (1-s+1e-8)
结果 = MIX(d, DODGE_BG(s,d), a)
```

DODGE_BG 不在 alpha 插值前提前裁剪；不得直接以 Canvas `color-dodge` 替代。SystemUI 的 DODGE（shader编号4）是另一个带 alpha 的 `colorDodgeBlend`，浅色通知最后一步必须根据归档 shader 处理调用参数与 alpha，不能替换成上述 DODGE_BG（编号3）。两者的完整源字符串已收录在 [系统证据摘录](evidence/systemui.md)，可按 `BLUR_DRAWABLE_SHADER_STRING_ALGORITHM_DODGE` 查找。

LUMINOSITY 对整个 RGB 向量计算：

```text
L(v) = 0.3R + 0.59G + 0.11B
target = L(s)
c = d + target - L(d)

若 min(c) < 0：
  c = target + (c-target) × target / (target-min(c))
否则若 max(c) > 1：
  c = target + (c-target) × (1-target) / (max(c)-target)

结果 = d × (1-a) + c × a
```

必须保留原生 if / else-if 的越界处理语义，处理黑/白等退化输入并确保有限输出。不要用独立 HSL 调整、降低 saturation 或普通灰色覆盖来近似这一公式。

**LUMINOSITY 不能使用当前每个通道独立的256项查找表。**亮度和越界修正依赖同一像素的三个通道；应在共享纹理生成时逐像素处理，单次 `getImageData` / `putImageData`。Launcher 的可分离两步仍可保留通道 LUT。不要每帧、每个文件夹或每次滚动重新做颜色变换。

SystemUI 的实际 shader 允许旧 bg/fg 参数在四步数组之前追加步骤。此候选只实现明确选择的四步，不声称覆盖所有设备后端。对应公式参考值：中灰 `#808080 → #262626`、白 `#FFFFFF → #2E2E2E`、蓝 `#096692 → #012F44`，仅在总报告声明的输入假设下成立。

## 6. 同步、性能与辅助显示

1. 复用一个共享纹理，并保持 `.folder-icon-surface, .launchpad-material-surface` 的统一同步。
2. 缓存需要随壁纸、视口、主题、背景蒙版和模糊参数变化失效；若增加可切换策略，策略也必须参与缓存键，不能依赖用户手动切换材质刷新。
3. 拖动和滚动只更新纹理坐标；移动/动画结束后停止持续刷新。窗口尺寸变化再重建纹理。
4. 右键前景副本和门户节点必须刷新共享背景，清除复制的旧局部纹理及 `important` 覆盖，避免副本颜色停在旧主题。
5. 关闭纵向渐变时同步检查背景层数及 size/position 列表；可保留透明 `none` 层以维持现有同步契约，确认无用途后再一起简化，不能只改 CSS 而错移壁纸层。
6. 保留减少透明度与强制颜色模式：前者提供稳定实色，后者使用系统色和必要边界，并恢复搜索文字的可读前景色。
7. 无壁纸、解码超时、Canvas 不可用、读取失败、快速切换与取消时，都应释放旧观察器/资源并允许恢复。

## 8. 验收边界与不应采用的捷径

完成后的说明必须同时回答：采用哪种表面配方、有哪些平台适配、哪些检查实际通过、哪些真机差异仍未知。

不应采用的做法包括：在深色公式后任意加20%/25%黑色并称其为原生参数；把回退色叠到完整纹理上；对搜索框单独增白或增黑；把 top/bottom 翻译成上下渐变；把应用图标暗色底图当成文件夹；以高斯模糊半径解决纯色背景没有纹理的问题；把静态公式相同写成屏幕观感已经一致。

后续若需要定位特定手机“更黑”的原因，优先取得该设备的主题/图标设置、材质与描边开关、能力分支、壁纸及取样状态等直接证据。现有未知项不会因文档归档或数值测试通过而自动消失。
